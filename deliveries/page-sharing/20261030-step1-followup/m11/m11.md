# M11：设备完成与 checkpoint 冻结

状态：独立真实 KVM 的 B0/File 与 B1/共享 NBD 设备回归、最终源码一致性重建与复验均已通过。这里验证异步块设备与网络 RX，不替代编排器应用 rootfs/原 trace 验收。

## 发现与修复

原 FC 在 `Vmm::save_state` 保存 vCPU/GIC 后，直到 MMIO 设备序列化才 `block.prepare_save`。后者排空异步读写、更新 guest RAM/virtqueue used ring 并发出完成 IRQ。结果是保存的 GIC 早于保存的 RAM/设备完成状态，恢复会缺完成 IRQ。目标 ARM64 的严格旧二进制回归 `m11-baseline-strict` 复现：网络 RX 持续增长，但四个 O_DIRECT worker 完成计数停滞，30 秒内无法恢复进展。未扩大 timeout。更早 `m11-run-modules` 与 `m11-no-native` 的失败保留；后者排除了二次 native oracle 特有问题。

修复先完成设备准备，再保存 vCPU/GIC，最后只序列化设备状态：

1. `MMIODeviceManager::prepare_save_devices` 排空 in-process block 的异步 I/O、刷盘和完成处理；block flush 错误返回到 `create_snapshot`，失败时不产生 state/RAM。
2. vsock transport reset 也前移到同一准备阶段；guest event RAM、used ring 与 IRQ 的状态在 GIC 捕获前完成。原先被日志吞掉的 guest 写入/used-ring 错误改为向上传播。
3. vsock reset 在同一暂停区间幂等，Resume 后清位；只有成功后才置已发送标志。构造/恢复不持久化该运行态标志。
4. native/internal 与 external checkpoint 均执行准备；external 冻结持续覆盖后续外部完整 RAM 导出。

兼容边界：activated vsock 若无可用 EVQ 描述符，checkpoint 现在明确拒绝；未激活设备不发送 reset。该行为避免返回不完整 checkpoint。vsock 连接采用原有 transport-reset 语义，不承诺 live 连接跨恢复延续。vhost-user checkpoint 仍不受支持。

## 测试与 oracle

新增 `m11_guest.go`：匹配 Debian 6.1.0-50-arm64 内核的 virtio-mmio/block/net 模块；四个 worker 对各自独立区域以 O_DIRECT 做 64 KiB 写入/读回，校验每个字节；另一个 raw Ethernet worker 校验 host TAP 注入的 payload 并递增接收计数。guest 2 vCPU / 128 MiB；独立可写 raw virtio-blk 镜像 16 MiB，Async io_engine。实际 `/proc/<FC pid>/fd` 必须存在 io_uring FD，不能只以配置请求作为 Async 证据。

新增 `m11_check.py`（复用 `kvm_check.py` 的受限导出/VM 生命周期工具）：

- 从同一 seed RAM/state/disk 恢复 B0/File 和 B1/共享只读 NBD；每组恢复后的完成计数必须超过先读取的 fresh status，不能把 seed 的累计计数当成恢复进展。
- 每组连续 3 次 Pause → external snapshot，host 网络注入全程继续；每个冻结边界连续采样 3 次完整逻辑 RAM hash 与磁盘 hash，要求全部稳定。
- 每次都与同一冻结状态的 FC native full dump 全量 hash 相等；离线逐字节检查所有非零磁盘记录的 worker/seq/slot/内容，复制磁盘也要求 hash 相等。
- 从最终 state/RAM 恢复后，四个 worker 和网络 RX 均须出现新完成；再做一次冻结全量 oracle，错误计数始终为零。
- B1 核对 ready source identity、logical size；记录进程 PID、NBD 路径/lease、完整 API/serial 日志、PSS/RSS/VmSwap/fault CSV 与 cleanup 回执。只操作自有 VM/helper/TAP。

新增 5 项 Rust 公有合同测试：真实 Async READ 在 `Vmm::save_state` 之前 pending，返回时 RAM/used ring 完成且 saved GIC 等于 post-drain GIC、不同于 pre-drain GIC；真实 `/dev/null` fsync EINVAL 使 native/external create_snapshot 拒绝发布；vsock reset 成功、同冻结区间幂等/Resume 清位、空队列持续失败和短描述符写失败。全部已在目标 sudo 运行通过。

## 构建及证据边界

Rust 1.85.0，aarch64-unknown-linux-gnu；`LIBRARY_PATH` 只指向已有 libseccomp 开发链接目录。该 GNU 构建使用仓库 unimplemented seccomp fallback，不能充当生产 musl/seccomp 包装验收。

中间一次 standalone rustfmt 递归触及远程隔离源码的 105 个未修改文件；本地工作树未受影响。它们已恢复成本地 baseline 原字节；最终执行 `--config skip_children=true --check` 仅检查 7 个修改文件，并以 `fc-source-sha256.txt` 检查全部 tracked Rust/Cargo 源码一致后重新构建。`remote-format-restored-files.txt` 记录恢复范围；中间 run 与最终 source-matched run 分开保留。

本测试的 writable virtio-blk 是 raw 测试盘，guest initramfs 为根目录。磁盘一致性与真实设备并发写已验证，但应用 rootfs 文件系统/编排器 Pause/发布链路及原 trace 的结论由相应独立 E2E 报告给出。未执行 live vsock 流量测试，不将三项 vsock 合同测试称为目标连接回放验收。

## 复现

`m11_setup.sh GO_BINARY MATCHED_MODULE_ROOT NEW_FIXTURE_DIRECTORY` 会只复制上述 5 个 `.ko`、构建静态 guest，并拒绝覆盖已有目录。模块必须与指定 kernel 匹配；本次输入为 `/home/coder/projects/yangshengxin/e2b/memory-lab-template-20261029-r4/root/lib/modules/6.1.0-50-arm64/kernel`，原目录只读使用。

```sh
sudo -n python3 scripts/memory-lab/page-sharing/m11_check.py \
  --firecracker /path/to/firecracker-source-matched \
  --kernel /home/coder/tide-repro/assets/vmlinuz \
  --guest-binary /path/to/new-fixture/m11-guest \
  --nbd-helper /path/to/page-sharing-source \
  --module-dir /path/to/new-fixture/modules \
  --output /path/to/NEW-run-directory --cleanup-failed
```

诊断模式 `M11_DIAGNOSTIC_SKIP_NATIVE=1` 仅用于缩小复现，结果只能标记 `diagnostic`，不可用于 M11 验收。目标旧 baseline 不设置该变量；严格新脚本对旧 baseline 应失败，修复二进制应通过。
